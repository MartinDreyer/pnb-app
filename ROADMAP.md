- Added an offline fallback cache so `index.html` no longer hard-fails on boot when `pnb-database`/Supabase is unreachable (e.g. airplane mode, or the local dev stack not running): `fetchActivePuzzle`/`fetchPuzzleById`/`fetchNumberedPuzzleHistory` now cache their successful results to `localStorage` and fall back to the last-cached value on a network error instead of throwing, and a new `fetchWithAssetCache`/`resolveImageBlobUrl` pair (backed by the Cache Storage API, `window.caches` — available in WKWebView without a service worker) does the same for actual asset bytes (`loadSvg`, and the reference images used by the home hero thumbnail, archive/history thumbnails, and the completion reveal), converting them to `blob:` URLs so they render fully offline once previously seen. A puzzle that's never been loaded before (or a first-ever launch with no network at all) still fails as before — this only fixes re-loading something the app has already fetched at least once. Offline behavior isn't a full sync gap indicator (no "not synced" UI), just silent graceful degradation to last-known-good data; a puzzle published while offline simply won't appear until the next successful fetch. Also tried, and then reverted, `"server": { "iosScheme": "https" }` in `capacitor.config.json`: the theory was that Capacitor's default iOS WebView origin (`capacitor://localhost`) isn't reliably treated as a secure context by WebKit, under which `window.caches` can silently no-op, and switching to `https://localhost` (matching Android's existing default) would fix that. Instead it broke image loading entirely, on-device — most likely because the cross-origin `fetch()` calls to Supabase Storage lost a CORS allow-listing keyed to the `capacitor://localhost` origin specifically. Reverted immediately once confirmed broken; `resolveImageBlobUrl`/`fetchWithAssetCache` already degrade gracefully when Cache Storage isn't available (plain fetch, no caching) so this doesn't block image loading — it just means the Cache-Storage-backed image caching may not actually work under iOS's default scheme, with only the localStorage SVG-text fallback reliably covering the offline case. Left as a known limitation rather than re-attempting the scheme change; a real fix (if pursued later) would need to keep the `capacitor://` origin and find another route to a secure context, or verify Supabase's CORS config against both origins first.
- Investigated a bug (found via a user-supplied screen recording, same frame-extraction-with-`imageio` technique as the 2026-09-15 stale-viewport entry above): pressing the home/back button from a puzzle would sometimes return to a home screen where every thumbnail frame — and even a plain static heading with no image/network dependency at all — rendered with zero visible size, while the plaque text beside them rendered fine; the screen became unresponsive until a full app relaunch (a mere `location.reload()` didn't self-heal). First theory was a recurrence of the 2026-09-15 stale-post-reload-viewport bug (`wireViewportSizeSync`'s double-rAF correction running too late against a fast local Supabase) — made `boot()` actually `await` that correction instead of firing it off unawaited, plus added `min-width`/`min-height` floors on the thumbnails as a backstop. That fix did **not** resolve it (confirmed via a second matching recording) — proving the theory wrong.
- Properly diagnosed the same bug by actually reproducing it, rather than continuing to theorize from source: spun up the local Supabase stack and a real browser (`puppeteer-core` driving the already-installed Google Chrome, since neither the Chrome DevTools extension nor a device Safari Inspector session was available) on the same dev machine, and replayed the exact puzzle→back-to-menu reload sequence against real data. It rendered perfectly — every thumbnail, the heading, everything — which rules out a logic/CSS bug entirely and confirms this is a WKWebView-runtime-specific rendering glitch (a known class of bug where some of the WebView's compositing layers occasionally fail to repaint at all after a `location.reload()`, especially with heavier CSS like the `.museumFrame` `conic-gradient` border-images and the new aspect-ratio-based thumbnail boxes — elements are correctly present and sized in the DOM, they just never get drawn). Tried the standard workaround for this bug class — a `forceRepaint()` helper (toggle `transform` on `.app`, force a synchronous `offsetHeight` read) called right as `boot()`'s `finally` block lifts the splash — but on-device testing showed the exact same glitch afterward (this time also taking out the menu's own logo/wordmark), so it wasn't fixing anything; reverted it rather than leave unproven, zero-benefit code in place, especially given toggling `transform` on an ancestor of several `position:fixed` overlays (splash/menu/archive) is its own known WebKit risk. Bug remains open — real progress needs an actual Safari Web Inspector session attached to the device, which hasn't been available yet. The still-good viewport-await fix from the earlier wrong-theory attempt was kept regardless, since it's a real (if not this bug's) improvement.
- Generator backend (`paintbynumbersgenerator-master/backend`) now renders a small JPEG thumbnail (max 320px, `canvas`) of each puzzle's reference photo alongside the full-resolution one, uploaded to the `puzzles` bucket at `<puzzleId>/thumbnail.jpg` and recorded in a new `puzzles.reference_thumbnail_storage_path` column (`pnb-database` migration `20260924090000_puzzle_reference_thumbnail.sql`, empty-string default so older rows fall back to the full image). `pnb-app`'s `fetchNumberedPuzzleHistory` (the archive/history grid) now points at the thumbnail instead of the full ~19MB reference photo, with a fallback to the full image when the thumbnail path is empty; the home hero thumbnail and completion reveal are unchanged since those already show the painting at a size where the full-resolution image is warranted.

## Next steps

- **Android launcher icons** — `android/app/src/main/res/mipmap-*/ic_launcher*.png` are still the default Capacitor placeholder; only the splash images were refreshed this round.
- **Package for TestFlight** — enroll the dev Apple ID in the paid Apple Developer Program ($99/yr); Personal Team accounts can't generate App Store distribution profiles.
- **History pagination** — `fetchPuzzleHistory()` is capped at the last 52 weekly puzzles with no pagination; revisit once real usage exceeds a year of history.
- **Timer** — track how long a user takes to complete a puzzle, start to finish.
- **Real rotation reliability** — even with the hourly coverage check, gaps ("no active puzzle") can still happen whenever the backend Node process itself isn't running (e.g. the dev laptop is off/asleep). The lasting fix is the "Cron-first puzzle prep" item below, not a shorter poll interval.
- **Lighter-weight SMK browsing** — the control panel feels heavy when listing multiple candidate paintings. SMK's search API already returns an `image_thumbnail` field alongside `image_native`, but `smkClient.ts`'s `mapItem` currently prefers `image_native` (full resolution) even for browse/search listings. Fix: use `image_thumbnail` for search/random listing previews, and only fetch `image_native` for the one painting actually chosen for generation.
- **Cron-first puzzle prep** — the control panel's manual generate/publish flow should become the override, not the primary path. Default operation should be a scheduled job (daily or weekly, configurable) that prepares and publishes the next puzzle automatically. Note: `ensureDailyPuzzleCoverage`/`runDailyPreparation` in `backend/src/server.ts` already implement a startup + 24h-interval coverage check — next step is making the cadence configurable (daily vs. weekly) and moving scheduling off "only runs while the Node process stays up" onto a real OS/hosting-level cron for reliability.
